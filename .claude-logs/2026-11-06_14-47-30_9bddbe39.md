Task:
Fix the native `PixelBackdrop` (`apps/mobile/components/pixel/PixelBackdrop.tsx`) so the students always stand on the sheet's edge.

**The bug:** the component captures its first state in `useRef(state).current` before `useSheetFloor` has measured the sheet, so `floor` is `null` at that point. The `useEffect` that injects `window.__backdrop(...)` runs before the WebView page has loaded, when `window.__backdrop` doesn't exist yet, so that update is dropped. The floor only arrives once some later change, like a raised hand, sends the state again. Until then the students stand at the scene's default `headY` and `scale` instead of on the sheet.

**The fix:** keep the latest state in a ref, and re-inject it in `onLoadEnd`. `PixelBoard.tsx` beside it already does this.

**Then check every screen that passes a floor**, in the iPhone simulator, because the students will move: onboarding (`app/index.tsx`), the warm-up (`app/warm-up/[gapId].tsx`) and the class steps (`components/class/ClassStep.tsx`). # Performance report: making Chalkback feel instant

I left out video reading and AI calls, as you asked. Everything below comes from the code on `main` plus real timings I took this session. I added temporary query logging, then removed it, and nothing in the code is changed.

## What I measured

| What | Result |
|---|---|
| **Where the API runs** | Vercel **Dublin** (`dub1`), reached through a **Mumbai** edge (`bom1`) from here |
| **A request that does almost nothing, in production** | 0.4–1.4 s (warm 0.4–0.55 s; first hits about 1–1.4 s, which suggests cold starts) |
| **Home's three calls, warm, local API** | topics **3.0 s**, due warm-ups **3.5 s**, session **3.1 s** |
| **Checking the sign-in token** | 270–420 ms, on **every** request |
| **One database query** | about **0.8 s** from here: 4–5 round trips at ~165 ms each |

Local timings exaggerate the database part. This Mac is about 165 ms from the database, while the production API is probably close to it. A ~165 ms round trip from Pakistan fits an EU database, which would match the Dublin functions, but I couldn't confirm it. Check the database region in the Supabase dashboard. The **number** of round trips is real either way, and every one of them adds up.

## Where the time goes

1. **Each query costs 4–5 round trips instead of 1.** The logs show every query wrapped as `BEGIN` → `DEALLOCATE ALL` → the query → `COMMIT`. That comes from Prisma's `pgbouncer=true` mode plus nested selects running as separate queries inside a transaction.
2. **"Parallel" queries actually wait in line.** The connection string sets `connection_limit=1`, so the `Promise.all` in `/topics` runs one query at a time.
3. **Every request checks the token with Supabase over the network** (`requireUser` → `auth.getUser`, [require-user.ts](apps/web/src/server/auth/require-user.ts)).
4. **Due warm-ups run one extra query per due gap** to find who asks ([warm-ups/session.ts:55](apps/web/src/server/warm-ups/session.ts:55)). A single-query version (`askersForTopics`) already exists from #64.
5. **The topic page loads the full transcript to return 3 fields.** `getTopic` and `getTopicGaps` call `findById`, which selects `segments`, then return only id, title and YouTube id. Opening a class does the same.
6. **The app keeps no cache between launches.** React Query starts empty on every launch, so Home always opens on skeletons and waits about 1–3 s.
7. **The class asks again for what Home already knows.** Home's topic list already includes `open_class_id` and the title, but the class route still calls `openClass` every time (`gcTime: 0`). That's why the new loading screen shows at all.
8. **Each screen starts a new WebView for its background.** Each one loads a 41 KB page and stays hidden until it's ready, so backgrounds visibly pop in on every screen change. Home, the memory board and reading each run **two** WebViews: the background plus a small portrait.
9. **The session call runs on every launch** and writes to the database each time (`last_seen_at`, an analytics check).
