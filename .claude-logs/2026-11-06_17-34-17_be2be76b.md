# Events

**Instrumentation is not a follow-up task.** A feature that ships without events cannot be
judged, and the week-5 kill/scale decision reads from the numbers this repo reports. A screen
with no events is a screen nobody can defend.

This skill runs **before** the feature code, not after.

## The one rule

> Every user-visible change registers its events in its app's registry **first**, then fires
> them from the code you write. No event fires that is not in the registry.

Each app has its own registry, and each is the single source of truth for that app:

- **Web:** `apps/web/src/lib/analytics/events.ts`. It types the `gaEvent()` call sites, and the
  server-side whitelist (`TRACKED_EVENTS`) is built from it. A name not in it is rejected by
  the beacon with a 400 and the data is gone silently — which is exactly how a play discovers
  six months later that its main funnel step was never recorded.
- **Mobile:** the `EventName` union in `apps/mobile/lib/analytics.ts`. It types the app's
  `track()` call sites, which go to PostHog. It is a separate list, not a mirror of the web's.

`npm run check:events` checks every call site against its own app's registry, in CI.

## Step 1: Read what already exists

Never invent a name that already has one. Start here:

```bash
cat apps/web/src/lib/analytics/events.ts    # web registry
cat apps/mobile/lib/analytics.ts            # mobile registry: the EventName union
npm run check:events                        # what is registered vs what is fired
```

Reuse an existing name if the moment is the same moment. Two names for one action means every
funnel built on it is wrong. A moment both apps record keeps one name in both registries
(`onboarding_completed`, `account_deleted`).

## Step 2: Ask for the events you cannot infer

Some events follow mechanically from the code (a screen mounts → `*_viewed`). Others encode a
product decision only the person asking can make. **Ask about these explicitly — do not guess:**

1. **What is the "aha" for this feature?** The single action that means it worked. This becomes
   the `user_activated` trigger or the feature's primary metric. If there is no answer, the
   feature has no success criterion and that is worth surfacing now.
2. **What is the drop-off you expect?** Each step you want to see people fall out of needs its
   own event, or the funnel has a gap you cannot see into.
3. **What discriminator does each event carry?** If an event can fire for different _things_
   (per pack, per lesson, per plan, per envelope), the id of that thing must ride in the
   metadata **and** be declared as a discriminator (Step 4). Without it, per-item counts are
   fiction: dedupe records the first one per day and drops the rest.
4. **Is this a money moment?** Purchases, trials, refunds and cancellations must also go to the
   Play Events API (Step 5) or the email automation for this play never fires.
5. **Does this change a user's lifecycle state?** Signup, activation, going inactive, deleting
   an account. These are the canonical events the platform already has flows for — use the
   canonical name, do not coin a new one.

Put the answers in the doc comment above the event group. The comment is not decoration: six
months from now it is the only record of why the event exists and what it was meant to prove.

## Step 3: Register, in the right group

Add to `apps/web/src/lib/analytics/events.ts` (web) and/or the `EventName` union in
`apps/mobile/lib/analytics.ts` (mobile). Names are `snake_case`, object-then-action
(`checkout_started`, not `start_checkout`).

```ts
/**
 * <Feature name> — <what this group is judged on, in one sentence.>
 *
 * <Which of these is THE metric and why. What question each one answers that
 * would otherwise be unanswerable.>
 */
export const FEATURE_EVENTS = {
	/** <When exactly it fires.> metadata: { thing_id } */
	viewed: 'feature_viewed'
} as const

export const FEATURE_EVENT_NAMES = Object.values(FEATURE_EVENTS)
```

Then spread `FEATURE_EVENT_NAMES` into `ALL_EVENT_NAMES` at the bottom of `events.ts`. That one
list types `gaEvent()` and is the first-party whitelist: `TRACKED_EVENTS` in
`src/lib/analytics/record.ts` is `ALL_EVENT_NAMES`, so a group left out of it fails typecheck at
every `gaEvent` call and is rejected by `/api/track`. Never hand-list `TRACKED_EVENTS`; if some
events should be PostHog-only, narrow it with a filter there (see Step 4 for which).

On mobile, add the names to the `EventName` union; there is no second list to update.

## Step 4: Pick the sinks — this is the part that gets skipped

There are three, they answer different questions, and choosing wrong is invisible:

| Sink                                                   | Use it for                                                                  | Gets you                                                                                          |
| ------------------------------------------------------ | --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| **PostHog + GA4** (`gaEvent` / `track`)                | Everything. Always fire here.                                               | Funnels, session replay, the dashboard's PostHog connection                                       |
| **First-party** (`recordUserEvent` + `TRACKED_EVENTS`) | Anything you need per-person, historical, or segmentable in the admin panel | `retention.cohorts` on the Play Stats API, admin segments, and numbers that survive an ad blocker |
| **Play Events API** (`src/lib/plays/events.ts`)        | Lifecycle + money moments only                                              | The platform's email automation: welcome, abandoned checkout, trial expiry, win-back              |

Fire first-party for anything that is **judged over time or per person**. PostHog only sees
forward from the day it was installed; your own table already knows what happened last quarter,
and it is the only route to retention cohorts for a play with no PostHog.

How each app reaches the sinks:

- **Web:** one `gaEvent()` call fans out to PostHog, GA4 and the `/api/track` beacon, which
  persists anything in `TRACKED_EVENTS`. `recordUserEvent` is the server-side call, for moments
  no browser sees (a webhook, a server route).
- **Mobile:** `track()` goes to PostHog only. A moment the app needs first-party or on the Play
  Events API is emitted server-side by the web route the app calls (first-party under the web
  registry's name, Play Events under the canonical one): signup through
  `/api/lifecycle/session`, a consent change through `PATCH /api/app/v1/profile`.

If the event carries a discriminator, declare it in `EVENT_DISCRIMINATORS` in
`apps/web/src/app/api/track/route.ts`. The client is not allowed to choose the dedupe key — a caller
that sent a fresh discriminator per request would write unbounded rows — so the allowed set is
decided server-side, per event name, and everything else in `metadata` is dropped.

## Step 5: Money and lifecycle also go to the Play Events API

`user_signed_up` and `account_deleted` are mandatory for every play. If the play monetizes, the
Tier 2 subscription and purchase events are what the revenue email flows run on.

```ts
import { trackPlayEvent } from '@/lib/plays/events'

await trackPlayEvent(
	'subscription_started',
	{ id: user.id, email: user.email, plan: 'pro', country, marketing_consent: consent },
	{ plan: 'pro', price_cents: 999, currency: 'usd', interval: 'month', from_trial: true }
)
```

Money is **integer minor units plus an ISO 4217 currency**, never floats. Call it from the
server only — the ingest key must never reach a browser or a mobile client. See
`docs/EVENTS.md` for the full canonical catalog and the two cron-driven events.

## Step 6: Verify before you call it done

```bash
npm run check:events
```

This fails the build if a name is fired but not in its app's registry, if `EVENT_DISCRIMINATORS`
declares an event that doesn't exist, or if a Play Events call uses a non-canonical name. A name
registered but never fired is only a warning: registering ahead of the UI that fires it is
allowed, so read the warnings rather than trusting the green. It runs in CI too. A green check,
with every new name fired, is the definition of done for instrumentation.

Then confirm the play's end of the contract still holds:

```
"run integration_check on <play-slug>"
```

A dashboard MCP, if yours has one, audits what this play is actually serving right now and names the
exact fields it is not sending. Ask it rather than reading a spec that may have moved.

## Anti-patterns, all of which have shipped before

- **Firing an unregistered name.** The beacon 400s it, nothing surfaces, the number is blank for
  months. This is the single most common failure and the whole reason for the registry.
- **One event for a repeating thing, with no discriminator.** Records the first per day, drops
  every other one, and the per-item breakdown reads as real data.
- **Inferring paid status from webhook event types.** A sandbox purchase fires the same
  lifecycle events as a real sale. Use the `environment` field, or every TestFlight tester
  counts as a customer.
- **Sending rates instead of counts.** Send counts; the dashboard divides, because only it knows
  which cohorts are mature.
- **Adding the events after the feature.** By then the call sites are spread across the diff,
  the discriminators were never threaded through, and it gets deferred.

# Ship

Make landing work boring and safe: verified locally, committed in the standard format, pushed
to a branch, opened as a pull request with a description a reviewer can trust, and green in
CI. Then stop. **An agent never merges on its own.**

"Push to main" and "merge to main" mean "land this". Here that is a branch and a PR; say so in
one line and carry on. Never push to `main`, even when asked in those words, and don't read
them as an instruction to merge. An agent merges a pull request only when the person
explicitly tells it to merge that pull request ([step 10](#10-merge-only-when-told-to)).

## Golden rules

1. **Never push to `main`, never merge a PR on your own, never force-push** anything but your
   own branch, and never to get around a failing check or a protection rule.
2. **Gates before push.** A gate fails: stop, show the real output, fix it or report it. Never
   "push and see what CI says".
3. Never `--no-verify`, never a blind `git add -A` or `git commit -a` over a dirty tree. If
   the tree has changes unrelated to this task, say so and ask before sweeping them in.
4. Never stage `.env*` (except the examples), `*.p8`, `*.jks`, `*.keystore`, service-account
   JSON or a zip of credentials (`docs/rules/secrets.md`).
5. `/ship check` runs steps 1 to 4 and reports. It commits and pushes nothing.

## 1. Orient

```bash
git rev-parse --abbrev-ref HEAD && git status --porcelain && git fetch origin main
```

On `main`? Create a branch before committing anything, named for the change:
`git switch -c <type>/<short-kebab-name>` (`feat/paywall-annual-plan`, `fix/offline-banner`).
Behind `origin/main` and not pushed yet: rebase onto it now. Already pushed: never rewrite
it; merge `origin/main` in if you must.

## 2. Classify the change

List what changed (`git diff --name-only origin/main...HEAD` plus the working tree) and say,
in the report and later in the PR:

- **Mobile (`apps/mobile/` or `packages/`)**: does it ship as an **OTA update**, or does it
  **need a store build**, and why? The decision is `AGENTS.md`, "Mobile: OTA first", and
  `docs/rules/ota.md`: native code changed (a native dependency, `app.json` plugins,
  permissions, infoPlist, entitlements, icons, splash, identifiers or version, an `eas.json`
  build profile, an SDK or React Native upgrade) means a store build; so does anything OTA must not carry (a new product
  category, something to buy outside in-app purchase, a feature hidden from review, a new
  permission or privacy disclosure). Otherwise it is an OTA update. Say it plainly: "ships as
  an OTA update" or "needs a store build because <change>".
- **The non-negotiables** (`AGENTS.md`): a user-visible change has its events registered (the
  `events` skill runs before the feature, not now); a change under
  `apps/web/src/app/api/dashboard/v1/` was checked against the live contract from your stats
  dashboard; a write to `plan_type`, `premium_*` or a subscription row happens on the server and has
  been read twice.
- **Schema**: if `apps/web/prisma/schema/` changed, run the local replay in `local-review`
  (drift, `check:rls`, the database suites); CI writes the missing migration and
  `deploy-migrations.yml` applies it from `main`. Flag deploy ordering in the PR when app code
  depends on it (`docs/rules/migrations.md`). `supabase/migrations/` is frozen: it never
  changes.

## 3. Gates: the `local-review` skill

Run the `local-review` skill (`.claude/skills/local-review/SKILL.md`). Its command block is
exactly what CI runs, in CI's order, followed by the commit-message check and a manual pass
against the rules. Don't keep a second copy of that list here: when a gate is added, it is
added there and in CI.

Stop at the first failure. Report each gate's real result, not "it passed".

## 4. Store review, when the app changed

If `apps/mobile/` or `packages/` changed, run the `store-review` skill
(`.claude/skills/store-review/SKILL.md`). `local-review` runs it for you in its section 2 when
the app changed; use that verdict rather than running the skill twice. It runs
`npm run check:store`, applies the Apple and Google rule table to the diff, and ends in one
verdict:

- **SHIP**: carry on.
- **FIX FIRST**: stop. Fix the list, then run the gates again.
- **NEEDS A HUMAN**: carry on, and put the list in the PR (privacy labels, the Data safety
  form, review notes, a demo account).

If the change **needs a store build** (step 2), run the mechanical gate strict as well, before
any build or submission:

```bash
npm run check:store -- --strict
```

Under `--strict` a `~ pending` rule fails: App Review doesn't read
`scripts/standards-exceptions.json`. The `store-review` skill says when a pending rule may
still ship.

## 5. Commit: Conventional Commits

Follow `docs/rules/commits.md`: `type(scope): subject`, imperative, lowercase, no trailing
period, header at most 72 characters, details in the body after a blank line. Types: `feat`
`fix` `perf` `refactor` `style` `docs` `test` `build` `ci` `chore` `revert`. The scope is
optional and one of the curated scopes in `scripts/check-commit-message.mjs`: `mobile` `web`
`api` `auth` `db` `events` `paywall` `onboarding` `admin` `ota` `store` `brand` `i18n` `ci`
`docs` `deps`. A change spanning areas takes no scope.

```text
feat(paywall): offer the annual plan with its monthly price

fix(mobile): keep the offline banner above the tab bar
```

The subject can still say what changed for the person using the app, in plain words.

- **Stage by path**, deliberately. A few commits per PR, each one unit of work; formatting and
  logic never share a commit. Not one commit per fix: batch the fixes.
- The `commit-msg` hook checks the format and CI's `commits` job checks it again over the whole
  branch. A rejected message is rewritten, never bypassed.
- **Session logs (in a play):** stage `.claude-logs/` separately, just before the push. The
  template repository itself keeps none (`CLAUDE.md`).

## 6. Push the branch

```bash
git push -u origin <branch>
```

Never `main`. If the push is rejected because the branch moved, fetch and integrate; never
force.

# Local review

A pre-push gate: the same checks CI runs, plus a manual pass against the rules CI can't fully
automate. Run it once a change is functionally done, not after every edit.

**This is what makes `docs/rules/commits.md`'s don't-over-commit rule work.** Every push runs
paid CI. This skill exists so CI _confirms_ what is already verified, instead of being the first
place a lint error, a type error or a broken build is discovered. If it is clean, commit once,
not once per fix.

## 1. Automated gates, in CI's order

These are exactly the commands the `check` job in `.github/workflows/ci.yml` runs on every pull
request, in the same order. A gate added to one is added to the other in the same PR, and
`check:standards` holds them to it: `local-review-mirrors-ci` reads both lists from the files,
and fails when this skill leaves out one of that job's gates, runs them in another order, or
runs a gate no CI job runs.

Stop at the first failure and fix it (or report it) before continuing. Don't run everything
blind and hand the user five unrelated failures. Report each command's real result, not "it
passed".

```bash
npm run check:secrets    # every tracked file, session logs included
npm run check:template   # the template tracks no session logs or worktrees; a play passes
npm run typecheck        # web, mobile, @app/contract and @app/brand
npm run lint             # 0 errors and 0 warnings (--max-warnings=0)
npm run format:check     # if this fails, run `npm run format`: always safe, never ask first
npm run check:standards  # the standards checklist (docs/STANDARDS.md)
npm run check:events     # every fired event is in its app's registry; unfired ones only warn
npm run check:env        # every env read is declared in the schema and .env.example, and vice versa
npm run check:store      # the store-review rules a file can decide (section 2 does the rest)
npm test                 # scripts, mobile Jest (+ packages/brand), the web and @app/contract suites
npm run web:build        # the Next.js production build
```

The build leaves `apps/web/.next/` behind; delete it afterwards if disk is tight.

Then the commit messages, the same check CI's `commits` job runs over the branch:

```bash
git fetch origin main
node scripts/check-commit-message.mjs --range origin/main..HEAD
```

Then the database gates, the ones CI's `migrations` job runs. They read a database with the
migrations applied, not the files, so they need a replay: a throwaway local Postgres, never a
shared or production one (Prisma needs a user name in the URL, or it fails with `P1010`):

```bash
createdb app_replay
psql -d app_replay -v ON_ERROR_STOP=1 -q -f apps/web/prisma/ci/supabase-shim.sql
export DATABASE_URL="postgresql://$USER@localhost:5432/app_replay" DIRECT_URL="postgresql://$USER@localhost:5432/app_replay"
npx prisma migrate deploy --schema apps/web/prisma/schema && npm run db:run-once
npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel apps/web/prisma/schema --exit-code
npm run check:rls        # RLS on, no policies, nothing granted to anon or authenticated
TEST_DATABASE_URL="$DATABASE_URL" npm run test:db --workspace=@app/web   # as a non-superuser
dropdb app_replay
```

none. A schema change with no migration shows up in the drift check; CI generates the
migration (`docs/rules/migrations.md`), and `node scripts/generate-migration.mjs --check

  inner-joins `analytics_events` or `analytics_pageviews` to `profiles`; no `v1` response
  shape changed; a new table has its security migration.
- **Auth** (`docs/rules/auth.md`, `docs/rules/authorization.md`): identity from the verified
  session or bearer token, never from the request body; an admin page sits under
  `admin/(protected)/`, whose layout guards it; every admin API route and server action calls

- **Secrets** (`docs/rules/secrets.md`): no value in `eas.json` or `app.json` (`app.json`

- **Logging and errors** (`docs/rules/logging.md`, `docs/rules/error-handling.md`): no new

- **Migrations** (`docs/rules/migrations.md`): a schema change doesn't break a column the app

- **DRY, the Rule of Three**: logic that already exists in two other files is extracted before

- **God files**: a changed file that now mixes routing, data access, business logic and

- **Naming**: camelCase for TypeScript, PascalCase for components and types,
