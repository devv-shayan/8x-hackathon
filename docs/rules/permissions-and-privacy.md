# Permissions and privacy

What the app asks the phone for, what it sends off the device, and how the store forms get
filled in from that. The mechanical checks are in `check:store`; the judgement is
in [store review](store-review.md).

## Purpose strings (Apple 5.1.1)

- **Every permission the app can request has a purpose string**, set through the module's
  config plugin in `apps/mobile/app.json` (for `expo-image-picker`: `photosPermission`,
  `cameraPermission`, `microphonePermission`). A missing one crashes the request on iOS.
- **Specific to this app, with an example**: "to upload a profile picture", "to scan
  receipts". Never "to access the camera". The template ships sentences a play replaces with
  its own; replacing them is part of cloning.
- **On iOS, set a string for everything the module's code can ask for**, even a path the play
  doesn't use yet: the reviewer's device can reach it. On Android, declare only what the app
  uses (below).

## Ask in context

- Request a permission at the moment it is needed, after the person has chosen the action that
  needs it. **Never at launch**, and never all at once in onboarding.
- **The app still works when a permission is denied.** Show what it can't do and how to turn it
  on in Settings; don't block the app.
- No pre-prompt that pressures, rewards or misleads ("Tap Allow to continue"). A short
  explanation screen before the system prompt is fine; a fake system prompt is not.

## Android: the narrowest permission

- **No broad media access.** `READ_EXTERNAL_STORAGE`, `WRITE_EXTERNAL_STORAGE`, `READ_MEDIA_*`
  and `MANAGE_EXTERNAL_STORAGE` are not declared unless the app's core purpose needs them and
  the standards exceptions file says why (Google Play's Photo and Video Permissions policy).
  Picking a photo uses the system photo picker, which needs no permission.
  `WRITE_EXTERNAL_STORAGE` does nothing on modern Android anyway.
- **`android.blockedPermissions`** keeps permissions that libraries' manifests would otherwise
  merge in out of the build. `CAMERA` (and `RECORD_AUDIO` for video) are unblocked only when a
  screen actually uses the camera. The one exception is automatic: with
  `EXPO_PUBLIC_RESEARCH_PRODUCT_KEY` set for the build, `research-widget.plugin.js` unblocks
  `RECORD_AUDIO` and adds `MODIFY_AUDIO_SETTINGS` for 8xResearch's voice interviews (AGENTS.md,
  "In-app interviews").
- A new permission is a native change: it needs a store build and a Data safety review
  ([OTA updates](ota.md)).

what its dependencies use. As shipped, it declares:

| File timestamp   | `C617.1`, `0A2A.1`, `3B52.1` | `react-native` (and its Folly, glog, boost pods), `@react-native-async-storage/async-storage`, `expo-file-system`, `expo-application`                           |

right-click the archive → Generate Privacy Report): that is what Apple aggregates, and what
the privacy labels must agree with. **Adding an SDK means updating this table and the manifest
in the same PR.**

## Tracking and App Tracking Transparency

"Tracking" in Apple's sense means linking what the app collects with other companies' data for
advertising, or sharing it with a data broker. As the template configures them, none of its
SDKs track, so it shows no ATT prompt and needs none. Adding an ads or attribution SDK, or
switching on RevenueCat's `collectDeviceIdentifiers()`, changes that: `expo-tracking-transparency`,
the prompt before the SDK starts, and "used to track you" in the labels. That is the first row
of the [store review](store-review.md) table, and `check:store` fails without it.

## What the play's own backend collects from the app

Not an SDK, but it is data collected from the app, so it belongs on the same forms:

- **`apps/web` (the play's own API and database):** the user id and email from sign-in; the
  person's **country**, derived from the request when the app announces a session
  (`/api/lifecycle/session` writes `profiles.region`: coarse location, linked); last-seen time;
  profile content the person enters; first-party analytics events (`analytics_events`).
- **Your email/automation platform (Play Events API, server to server):** email, name, country, locale, plan
  and marketing consent, for the play's lifecycle and marketing email. Marketing flows send
  only with `marketing_consent`; `account_deleted` makes the platform purge the contact.
  Declare email as used for app functionality and, with consent, developer marketing.

## Filling in the forms (NEEDS A HUMAN)

These live outside the repo, so an agent drafts and a person submits:

- **App Store Connect privacy labels** and the **Play Data safety form**, from the two sections
  above. Whether PostHog stores IP addresses is a PostHog project setting, not code: check it,
  and declare coarse location if it does.
- The **privacy policy** (`apps/web/src/app/privacy/page.tsx`, and the app's `privacy` screen)
  names the same processors the tables do. When a row is added here, the policy changes in the
  same PR.
- **Play's account-deletion web link** points at `/delete-account` on the play's site.

## Web, for completeness

The marketing site loads PostHog (`posthog-js`), Google Analytics 4 (when `NEXT_PUBLIC_GA_ID`
is set) and Vercel Web Analytics. They are the website's privacy policy and cookie-consent
concern, not the app's labels; the same "no personal data in event properties" rule applies
([analytics](analytics.md)).
